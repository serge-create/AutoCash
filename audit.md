# Аудит проекта AutoCash

**Дата аудита:** 2026-06-11  
**Версия проекта:** WPF .NET Framework 4.7.2 + Entity Framework 5.0  
**Цель:** Выявление критических багов, уязвимостей безопасности и архитектурных проблем.

---

## 1. Критические проблемы безопасности (Critical)

### 1.1. PIN-коды хранятся в открытом виде (вне хеширования)
**Файл:** `AutoCash/Models/Employees.cs`, `LoginWindow.xaml.cs`, `EmployeeManagerWindow.xaml.cs`  
**Проблема:** Пароли/PIN-коды сотрудников хранятся в БД и сравниваются как открытый текст (`e.PinCode == password`). Отсутствует хеширование (bcrypt, PBKDF2, SHA256+salt). Любой администратор может прочитать PIN сотрудников, а утечка БД = компрометация всех учетных записей.  
**Рекомендация:** Внедрить хеширование PIN-кодов с солью. При входе сравнивать хеши, а не plaintext.

### 1.2. Захардкоженный мастер-пароль инициализации
**Файл:** `AutoCash/Views/LoginWindow.xaml.cs:45`  
**Проблема:** Пароль первичной инициализации `"123456789"` захардкожен в коде. При декомпиляции сборки пароль становится известен. Любой, у кого есть доступ к БД, может пройти инициализацию.  
**Рекомендация:** Вынести в конфигурацию с обязательной сменой при первом входе, либо генерировать случайный пароль и выводить в консоль/лог.

### 1.3. PIN-коды отображаются в интерфейсе в открытом виде
**Файл:** `AutoCash/Views/Management/EmployeeManagerWindow.xaml.cs:61`  
**Проблема:** Поле `txtPinCode` — обычный `TextBox`, а не `PasswordBox`. PIN-код сотрудника виден на экране при редактировании.  
**Рекомендация:** Заменить `TextBox` на `PasswordBox` для поля PIN.

### 1.4. Отсутствие защиты от брутфорса
**Файл:** `AutoCash/Views/LoginWindow.xaml.cs`  
**Проблема:** PIN-коды состоят из 6-9 цифр (низкая энтропия), и нет механизма блокировки после N неудачных попыток. Брутфорс 6-значного PIN займет секунды.  
**Рекомендация:** Ввести блокировку учетки после 3-5 неудачных попыток, логировать попытки входа.

### 1.5. Строка подключения к БД с открытыми данными
**Файл:** `AutoCash/App.config:10`  
**Проблема:** 3 дублированные connection strings с жестко прописанным именем сервера `RAYVON` и `integrated security=True`. В коммерческой среде это приводит к зависимости от имени машины и локального аккаунта Windows.  
**Рекомендация:** Использовать SQL-аутентификацию с шифрованием строки подключения, либо вынести в пользовательский конфиг.

## 2. Критические баги (Critical)

### 2.1. NullReferenceException при оплате (потеря чека)
**Файл:** `AutoCash/Views/MainWindow.xaml.cs:267-268`  
**Проблема:**
```csharp
var paymentType = db.Payment_Types.Where(x => x.Name == paymentMethod).FirstOrDefault();
int paymentTypeId = paymentType.PaymentTypeID; // NRE если paymentType == null
```
Если в БД нет записи с `Name == "Наличные"` или `"Карта"`, приложение упадет с `NullReferenceException` и потеряет весь чек (который уже собран в `_cartItems`). Чек не сохранится.  
**Рекомендация:** Добавить проверку `if (paymentType == null) { MessageBox.Show(...); return; }`

### 2.2. Разрыв транзакции при закрытии смены (Z-отчет)
**Файл:** `AutoCash/Views/Management/ShiftManagerWindow.xaml.cs:132-144`  
**Проблема:**
```csharp
PrintZReport();        // Если здесь исключение — смена в БД НЕ закрыта,
db.SaveChanges();       // но AppState.CurrentShift = null уже вызван!
AppState.CurrentShift = null;
```
Если `PrintZReport()` выбросит исключение, `db.SaveChanges()` не выполнится, но `AppState.CurrentShift` будет сброшен. Пользователь увидит "Смена закрыта", но в БД она останется открытой. Это критично для кассовой дисциплины.  
**Рекомендация:** Сохранить `db.SaveChanges()` **до** `PrintZReport()`, либо использовать `TransactionScope` и откат.

### 2.3. Отладочный MessageBox в production-коде
**Файл:** `AutoCash/Views/MainWindow.xaml.cs:261`  
**Проблема:** `MessageBox.Show(paymentMethod);` — оставленный отладочный вывод, который будет показываться кассиру при каждой оплате.  
**Рекомендация:** Удалить строку.

### 2.4. Пустой блок кода (синтаксическая ошибка/мусор)
**Файл:** `AutoCash/Views/MainWindow.xaml.cs:68-72`  
**Проблема:**
```csharp
if (e.Key == Key.F8) { btnPayCard_Click(null, null); return; }
{

}
```
Пустые фигурные скобки после условия — бессмысленный код, который может сбить с толку при рефакторинге.  
**Рекомендация:** Удалить пустой блок.

## 3. Проблемы целостности данных и бизнес-логики (High)

### 3.1. Нарушение финансовой целостности при удалении товара
**Файл:** `AutoCash/Views/Management/ProductManager.xaml.cs:221-241`  
**Проблема:** При удалении товара, связанного с чеками, код удаляет позиции из старых чеков и вычитает `SubTotal` из `TotalAmount`. Это **изменяет исторические финансовые данные** — нарушение бухгалтерской целостности. Старые чеки должны быть неизменны. Также не учитывается `ReceiptDiscount`, и может получиться отрицательный `TotalAmount`.  
**Рекомендация:**
- Запретить удаление товаров, участвовавших в чеках (мягкое удаление `IsDeleted = true`).
- Или создавать корректирующие записи, а не менять исторические чеки.

### 3.2. Нет проверки остатков на складе при продаже
**Файл:** `AutoCash/Views/MainWindow.xaml.cs:125-151`  
**Проблема:** Метод `AddToCart` увеличивает количество товара, но не проверяет, достаточно ли товара на складе. Кассир может продать больше, чем есть. Проверка остатка `StockQuantity` происходит только в `ProductSearchWindow` (при загрузке), но не при повторном добавлении того же товара.  
**Рекомендация:** Добавить проверку `existingItem.Quantity < product.StockQuantity` при каждом добавлении.

### 3.3. Нет проверки остатков при списании
**Файл:** `AutoCash/Views/MainWindow.xaml.cs:301-305`  
**Проблема:** При сохранении чека списывается `productInDb.StockQuantity -= (int)item.Quantity`, но `StockQuantity` может стать отрицательным, если между добавлением в корзину и оплатой товар закончился.  
**Рекомендация:** Проверить остаток перед списанием, либо использовать `TransactionScope` с `RowVersion` для оптимистичной блокировки.

### 3.4. Неатомарная операция сохранения чека
**Файл:** `AutoCash/Views/MainWindow.xaml.cs:259-319`  
**Проблема:** `SaveReceiptToDatabase` делает `db.SaveChanges()` дважды: сначала для заголовка чека, потом для позиций. Если между ними произойдет сбой (например, deadlock), чек будет создан без позиций. Нет `TransactionScope`.  
**Рекомендация:** Обернуть весь метод в `TransactionScope` (или использовать `db.Database.BeginTransaction()`).

### 3.5. Нет проверки, что смена открыта текущим пользователем
**Файл:** `AutoCash/Views/MainWindow.xaml.cs:96`, `ShiftManagerWindow.xaml.cs`  
**Проблема:** При входе восстанавливается любая открытая смена (`FirstOrDefault(s => s.ClosedAt == null)`), а не смена текущего пользователя. Если кассир А открыл смену, кассир Б может зайти и продолжить продажи в чужую смену.  
**Рекомендация:** Проверять `EmployeeID` открытой смены.

### 3.6. Дублирование connection strings (3 штуки)
**Файл:** `AutoCash/App.config:10`  
**Проблема:** `AutoCashierDbEntities`, `AutoCashierDbEntities2`, `AutoCashierDbEntities1` — дублируются, но код использует `AutoCashierDbEntities1`. Дублирование создает путаницу и риск использовать неправильный контекст.  
**Рекомендация:** Оставить один connection string, удалить лишние.

## 4. Средние проблемы (Medium)

### 4.1. Низкая энтропия PIN-кодов
**Файл:** `AutoCash/Views/Management/EmployeeManagerWindow.xaml.cs:195`  
**Проблема:** `GenerateUniquePin()` создает 6-значный PIN (1 000 000 комбинаций). Это слишком мало для системы безопасности. Для сравнения: банковские PIN — 4 цифры, но там есть блокировка и физический доступ к карте.  
**Рекомендация:** Увеличить до 8-10 цифр, либо использовать PIN + пароль для администраторов.

### 4.2. Не установлен Owner для диалоговых окон
**Файл:** `AutoCash/Views/MainWindow.xaml.cs:321-323`  
**Проблема:**
```csharp
new Management.ProductManager().ShowDialog();
```
`Owner` не установлен — окно может открыться за родительским, кассир может потерять его из фокуса.  
**Рекомендация:** `window.Owner = this` перед `ShowDialog()`.

### 4.3. Некорректное использование Entity Framework Find() в разных контекстах
**Файл:** `AutoCash/Views/Management/ProductManager.xaml.cs:173`  
**Проблема:** `_selectedProduct` загружен из одного контекста `using`, а `Find()` вызывается в другом. Хотя `Find()` работает по первичному ключу, это плохая практика (отслеживание объектов из разных контекстов).  
**Рекомендация:** Либо использовать один контекст на операцию, либо использовать `AsNoTracking()` при загрузке и `Attach()` при обновлении.

### 4.4. NullReferenceException при добавлении категории
**Файл:** `AutoCash/Views/Management/AddCategoryWindow.xaml.cs:32`  
**Проблема:** `g.Name.ToLower()` — если `Name` может быть `null`, будет NRE.  
**Рекомендация:** `g.Name?.ToLower() == categoryName.ToLower()`.

### 4.5. Некорректное обновление данных при удалении товара из чека
**Файл:** `AutoCash/Views/Management/ProductManager.xaml.cs:231`  
**Проблема:** `parentReceipt.TotalAmount -= item.SubTotal.Value` — если `TotalAmount` меньше `SubTotal`, получаем отрицательную сумму чека. Не учитывается возможная скидка на чек (`ReceiptDiscount`).  
**Рекомендация:** Проверять `TotalAmount >= SubTotal`, либо установить `TotalAmount = 0` как минимум. Но лучше не удалять товары из чеков вообще.

### 4.6. Сканер штрихкодов конфликтует с UI-элементами
**Файл:** `AutoCash/Views/MainWindow.xaml.cs:66-90`  
**Проблема:** `_barcodeBuffer` собирается в `Window_KeyDown`, но если фокус находится в `TextBox`, введенные цифры попадут и в TextBox, и в `_barcodeBuffer`. Кроме того, `Enter` используется для сканера, но также для навигации по UI.  
**Рекомендация:** Подписаться на `PreviewKeyDown` или использовать RawInput/USB HID для сканера, чтобы отличить его от клавиатуры.

### 4.7. Неиспользуемый using
**Файл:** `AutoCash/Views/PaymentWindow.xaml.cs:2`  
**Проблема:** `using System.Security.Cryptography.Xml;` — подключен, но нигде не используется.  
**Рекомендация:** Удалить.

### 4.8. Опечатка в комментариях
**Файл:** `AutoCash/Views/Management/ShiftHistoryWindow.xaml.cs:11`  
**Проблема:** `pubic` вместо `public` (это уже опечатка в коде, но в данном файле — не критично, если компиляция проходит).  
**Рекомендация:** Исправить опечатки в комментариях.

### 4.9. Заглушка фискализации без TODO
**Файл:** `AutoCash/Views/Management/ShiftManagerWindow.xaml.cs:157-161`  
**Проблема:** `PrintZReport()` — пустая заглушка. Если кто-то забудет реализовать, система будет считать, что Z-отчет напечатан, но он не будет передан в ФНС.  
**Рекомендация:** Добавить `throw new NotImplementedException()` или явную маркировку `// TODO`.

### 4.10. Некорректная логика поиска товара по штрихкоду
**Файл:** `AutoCash/Views/MainWindow.xaml.cs:107`  
**Проблема:** `FirstOrDefault(p => p.Barcode == barcode)` — если в БД несколько товаров с одинаковым штрихкодом, берется первый попавшийся. Это некорректно для торговли.  
**Рекомендация:** Добавить уникальный индекс на `Barcode` в БД, либо показывать список совпадений.

### 4.11. Скидки не применяются при добавлении в корзину
**Файл:** `AutoCash/Views/MainWindow.xaml.cs:139-147`  
**Проблема:** В `CartItem` есть поле `Discount`, но при добавлении в корзину оно всегда `0`. Поле `DiscountPercent` из `Products` нигде не используется. Скидка не работает.  
**Рекомендация:** Реализовать расчет скидки при добавлении товара.

### 4.12. Нет проверки единственности открытой смены
**Файл:** `AutoCash/Views/LoginWindow.xaml.cs:90`  
**Проблема:** `FirstOrDefault(s => s.ClosedAt == null)` — если в БД по ошибке оказалось 2 открытые смены, берется первая, что может быть не той сменой.  
**Рекомендация:** Проверять наличие только одной открытой смены, либо брать по `EmployeeID`.

## 5. Архитектурные и технические проблемы (Medium/Low)

### 5.1. Статический `AppState` без thread-safety
**Файл:** `AutoCash/Core/AppState.cs`  
**Проблема:** `CurrentUser` и `CurrentShift` — статические свойства. В WPF UI-поток один, но если будут фоновые операции, возможны race conditions.  
**Рекомендация:** Обернуть доступ в `lock` или использовать `ThreadStatic`/`AsyncLocal` если понадобится многопоточность.

### 5.2. Нет DI-контейнера, прямая зависимость от контекста БД
**Файл:** Весь проект  
**Проблема:** `new AutoCashierDbEntities1()` захардкожен в каждом View/Window. Тестирование невозможно без реальной БД.  
**Рекомендация:** Внедрить фабрику контекстов или DI-контейнер (Unity, Autofac, SimpleInjector).

### 5.3. Нет логирования ошибок
**Файл:** Весь проект  
**Проблема:** Все ошибки обрабатываются через `MessageBox.Show(ex.Message)`. Ошибки не сохраняются в лог, что затрудняет отладку в production.  
**Рекомендация:** Внедрить NLog, Serilog или log4net.

### 5.4. Entity Framework 5.0 (устаревший)
**Файл:** `AutoCash/packages.config`  
**Проблема:** EF 5.0 от 2012 года. Устаревший подход Database-First с `.edmx`. Нет поддержки async/await, миграций, новых возможностей EF Core.  
**Рекомендация:** Мигрировать на EF Core (для .NET 6+) или хотя бы EF 6.x.

### 5.5. Нет unit-тестов
**Файл:** Весь проект  
**Проблема:** Отсутствуют тесты для бизнес-логики (расчет сдачи, списание остатков, авторизация).  
**Рекомендация:** Внедрить MSTest/NUnit/xUnit.

### 5.6. Нет валидации на уровне модели
**Файл:** `AutoCash/Models/*.cs`  
**Проблема:** Все модели EF сгенерированы автоматически, без атрибутов валидации (`[Required]`, `[StringLength]`, `[Range]`). Валидация дублируется в код-behind окон.  
**Рекомендация:** Добавить Data Annotations или Fluent API валидацию.

### 5.7. Нет обработки изменения данных в фоне
**Файл:** `AutoCash/Views/Management/ProductManager.xaml.cs`  
**Проблема:** `_allProducts` кэшируется при загрузке окна. Если другой кассир изменит товар, изменения не отобразятся до перезагрузки.  
**Рекомендация:** Добавить кнопку обновления или таймер.

### 5.8. Нет защиты от конкурентных изменений (optimistic locking)
**Файл:** Весь проект  
**Проблема:** Два кассира могут одновременно редактировать один товар. Последний сохранит свою версию, перезаписав изменения первого.  
**Рекомендация:** Добавить `RowVersion`/`Timestamp` в таблицы и обрабатывать `DbUpdateConcurrencyException`.
